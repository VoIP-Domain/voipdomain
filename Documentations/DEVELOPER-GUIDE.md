# VoIP Domain – Developer Guide

> **Status:** Draft / WIP – feel free to extend and improve. The goal of this file is to give new contributors a bird's-eye view of how the codebase is organised and how to extend it effectively.

## 1. Architecture at a glance

VoIP Domain is split in three major, loosely-coupled parts:

1. **Administrative Interface** (PHP + NGiNX + MariaDB) – Web UI and RESTful API.
2. **Daemons** (CLI PHP) – AMI monitor, router, FastAGI, etc.; they communicate through Gearman.
3. **Asterisk servers** – run the dial plan generated by the Administrative Interface and receive live configuration updates through the daemons.

Everything is held together by a very lightweight **hook-based framework**.  Every feature – API endpoint, web page, background task – is just a PHP function that is *registered* in the framework and *called* through a hook.

```
framework_add_hook ( "<hook_name>", "<php_function>", <IN_HOOK_*> [, $opts] );
```

## 2. Hook style programming

### 2.1  Why hooks?
The hook system removes tight coupling between modules.  A module *publishes* capabilities (hooks) and *subscribes* to other hooks.  New behaviour can be introduced or overridden without modifying the core.

### 2.2  Standard hook life-cycle
For every CRUD-like action the framework automatically supports the following **standard sub-hooks** (remember them – you will use them all the time):

| Phase            | Purpose                               | Runs **if defined** |
|------------------|---------------------------------------|---------------------|
| `<hook>_start`   | First code executed.  May rewrite the argument array. | ✅ |
| `<hook>_validate`| Validate input.  Return `array("field"=>"error")` to abort with *422 Unprocessable Entity*. | ✅ |
| `<hook>_sanitize`| Normalise / cleanup parameters.        | ✅ |
| `<hook>_pre`     | Called just before DB interaction.     | ✅ |
| `<hook>_post`    | Called right after DB interaction.  Often used to reshape results. | ✅ |
| `<hook>_notify`  | (Optional) Push events to Gearman / AMI / WebSocket. | 🔄 |
| `<hook>_finish`  | Always executed at the very end.       | ✅ |

A single PHP file can implement **all** or **some** of those phases, according to its needs.

### 2.3  Non-standard / global hooks
The framework also fires a few general-purpose hooks that do **not** follow the previous naming scheme.  The most relevant ones are summarised below – you can attach to them to change core behaviour:

* `framework_page_generate` – last chance to tweak the rendered HTML before it is sent to the browser.
* `login_page_generate`, `install_page_generate` – allow theming / SSO extensions on the login & installer screens.
* `debug_call_hook`, `debug_explain`, `debug_api_map` – instrumentation & troubleshooting helpers.
* `ping` – cheap health-check endpoint used by load-balancers.
* `<module>_search_page`, `<module>_add_page`, `<module>_edit_page`, … – server-side rendering for the Web UI.  Those are *pages*, not API calls.
* `server_rebuild_config`, `router_reload_cache` – long-running infrastructure tasks triggered by other components.

Whenever you are unsure whether a hook already exists use the **Debug → "API Map"** page or the `GET /debug/api/map` endpoint to dump the whole tree.

### 2.4  Calling hooks manually

```php
if ( framework_has_hook ( "ranges_add_pre"))
{
  $params = framework_call ( "ranges_add_pre", $params);
}
```

## 3. RESTful API system

### 3.1  Definition & routing
Endpoints live inside `Administrative Interface/modules/<module>/api.php` files and are declared with

```php
framework_add_api_call
(
  "/ranges/:ID",           // path (supports :var syntax)
  "Read",                  // HTTP verb: Create | Read | Update | Delete | Custom
  "ranges_view",           // *main* hook that will implement the logic
  array (                  // extra options (permissions, docs…)
    "permissions" => array ( "User", "ranges_view"),
    "title"       => __ ( "View range details"),
    "parameters"  => [...], // used both for validation and for Swagger docs
  )
);
```

The first segment of the path (`/api`) is automatically added by the framework, so the actual URL becomes `/api/ranges/:ID`.

### 3.2  Versioning
Two equivalent mechanisms exist:

* Custom header `X-API-VERSION: <n>`
* Prefix the endpoint with `…/v<n>/…` (e.g. `/api/v2/ranges`)

### 3.3  Permissions & authentication

* **Session cookie** if the request originates from the Web UI.
* **Bearer token** (generated in *Tokens* module) for programmatic access.
* ACL is enforced with `framework_add_permission ( "<perm>", "Human text")` and then referenced in the `permissions` array of the endpoint.

### 3.4  Writing a new endpoint – checklist

1. Pick or create a module directory (copy `modules/example/` for a template).
2. Add a primary hook `<module>_<action>` implementing the business logic.
3. Optionally implement the standard sub-hooks.
4. Call `framework_add_hook()` to register each hook.
5. Call `framework_add_api_call()` to expose it through REST.
6. Refresh `/debug/api/map` – your endpoint must appear immediately.

### 3.5  Response format & status codes
Return **PHP arrays** or **scalars**; the framework turns them into JSON (`Content-Type: application/json; charset=utf-8`).  Stick to the HTTP codes described in `Documentations/API/api.txt` (200, 201, 204, 4xx, 5xx…).

### 3.6  Automatic API documentation
Every field given to `framework_add_api_call ()` (title, description, parameters, schema, examples…) is stored in an internal structure that is exported as **OpenAPI 3.0**.  The static Swagger-UI bundle in `Documentations/swagger/` renders it at `/api/docs`.

To document a new endpoint just make sure `title`, `description`, `parameters`, and (optionally) `response.schema` are filled – nothing else to do.

## 4. Web Interface system

The PHP UI follows the same *hook* philosophy.  A page is composed by aggregating fragments contributed by multiple modules.

1. The router resolves the request to a *page hook* such as `extensions_view_page`.
2. Each module may prepend/append its own function to that hook (`IN_HOOK_INSERT_FIRST`, `IN_HOOK_NULL`, `IN_HOOK_INSERT_LAST`).
3. The final buffer is sent to the browser.

AdminLTE 3 is used for basic styling; jQuery 3.7, DataTables, Select2, etc. are vendored under `Administrative Interface/vendors/`.

### 4.1  Adding a new page

* Create `modules/<module>/webui.php`.
* Register a new page hook with `framework_add_hook ( "<module>_<page>_page", "<function>", IN_HOOK_INSERT_FIRST);`.
* Return plain HTML.  For consistency wrap the main content in a `<section class="content">`.
* (Optionally) link JS/CSS via the `assets_enqueue_*` hooks provided by `modules/interface/`.

## 5. Plugin system

A *plugin* is just a PHP module placed under one of these roots:

```
Administrative Interface/modules/
Daemons/*-modules/
Plugins/
```

During bootstrap the framework crawls those directories, includes every `*.php` file and records the hooks they register.  Nothing else to configure – drop‐in, restart FPM (or the daemon) and you are done.

Plugins may:

* Register hooks / endpoints / pages.
* Ship static assets (JS, CSS, images).
* Extend translations via `language.php`.

Keep user-land plugins inside `Plugins/` – it avoids merge conflicts when updating upstream.

## 6. Installation & deployment

Detailed step-by-step instructions live in `Documentations/INSTALL.md`.  Below is the TL;DR for developers:

1. Clone repository;
2. Create an NGiNX vhost pointing to `Administrative Interface/` using PHP-FPM;
3. Access the vhost using a browser;
4. Install database and system configuration;
5. Launch daemons with the provided `systemd/*.service` templates (`Daemons/router.php`, `Daemons/monitor.php`, …);
6. First login: user *admin* / password *admin*.

The platform supports both **all-in-one** and **distributed** setups.  Read the *Installing all-in-one server* and *Installing Asterisk server* sections in INSTALL.md for caveats (file permissions, ACL on TLS keys, etc.).

## 7. Debugging & instrumentation

* `GET /debug/ping` → cheap health-check (returns `"PONG"`).
* `GET /debug/api/map` → full dump of routes, hooks and where they are implemented (file + line).
* `GET /debug/callhook/<Hook>` → execute any hook and inspect the raw JSON result.

Enable *debug* module permissions for your account inside the Web UI.

## 8. Coding conventions & tips

* Use **English** for code identifiers – translations happen through `__ ( ...)`.
* Never `include_once` manually; always rely on the automatic module discovery.
* Prefer **prepared statements** (`$pdo->prepare`) or the helper wrappers provided by the framework.
* Keep SQL portable (§ MySQL 5.6 / MariaDB 10.1 compatibility).
* Commit messages follow the style "**<module>: Short description**".

## 9. Useful entry points in the codebase

* `Administrative Interface/includes/framework.inc.php` – loader, hook dispatcher, helper functions.
* `Administrative Interface/modules/interface/` – base templates, login, asset pipeline.
* `Daemons/router.php` – main event router.
* `Daemons/monitor.php` – AMI listener, call detail collector.

## 10. API session variable

Session authentication data is stored in `$_in["session"]`. The structure is:

* $_in["session"]["Authenticated"] → Whether the user is authenticated. Before the authentication process it is set to `FALSE`, and `$_in["session"]["Method"]` is empty.
* $_in["session"]["Method"] → Authentication method. Possible values: `None` (no authentication, used after the process or in unauthenticated endpoints), `Session` (user session), `Token` (access token), `Server` (managed-server authentication), `AuthToken` (extension authentication), `Internal` (internal system call) or `Install` (installation process)
* $_in["session"]["Tenant"] → ID of session tenant context.
* $_in["session"]["Language"] → Session language.
* $_in["session"]["Timezone"] → Session timezone.
* $_in["session"]["Permissions"] → Session permissions array.
* $_in["session"]["Data"] → Variable session data array. The values will depend on authentication method used:
  * No authentication:
    - None
  * Session:
    - ID → User ID
    - Username → User username
    - Name → User name
    - Email → User email
    - Since → Date/time user created
  * Token:
    - ID → Token ID
    - Description → Token description
    - Access → CIDR access restrition
    - Expires → Date/time of token expiration
  * Server:
    - ID → Server ID
    - Description → Server description
    - PublicKey → Server public key
  * AuthToken:
    - Token → Authentication token
    - Plugin → Authentication plugin used
    - Email → Authentication email
    - IssueDate → Date/time of token creation
    - LastSeen → Date/time last token activity
    - Expires → Date/time of token expiration
  * Internal:
    - None
  * Install:
    - None

**Note**: The authentication methods can be extended through plugins or in new software releases.
